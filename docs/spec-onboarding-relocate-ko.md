## 현재 구조 (실제 코드 확인)

`hub/app/js/app.js`(TOPIK I 앱 전용)의 `goTab()`(1038행)이 `state.profile.onboardingDone`을 체크해 온보딩(`showOnboarding`)을 트리거. 이 로직은 **TOPIK I 앱(`hub/app/index.html`) 안에서만 동작** — Hangul(`hub/app/hangul/`)·Basics(`hub/app/basic/`)·TOPIK II(`hub/app/topik2/`)는 완전히 별개 미니앱이라 이 체크 자체가 없음(실측 확인 — localStorage 비운 뒤 Hangul 먼저 열면 온보딩 자체가 안 뜸).

온보딩 4단계(Basic info → 목표(TOPIK 응시 계획) → 모드 → 파트너) 중 **1단계(Basic info)는 범용 정보**(모국어·이전 학습기간·목표 학습량·일일 학습시간), **2단계(목표)는 순수 TOPIK 전용 정보**(응시 예정 여부·시기). 지금은 이 둘이 하나의 강제 시퀀스로 묶여 있음.

## Paul이 확정한 목표 동작

1. **공통 정보(모국어 등)** — jabi를 처음 쓰는 시점에 **트랙 무관하게 딱 1회**. 어느 트랙으로 처음 들어오든(Hangul이든 TOPIK I이든) 트리거되어야 함.
2. **TOPIK 응시 계획 질문은 온보딩에서 완전히 제거.** 대신: 학습자의 **진도가 TOPIK 응시를 논할 수준에 도달했을 때**, "내 페이지"(학습자 프로필/분석 화면)에서 **먼저 그 사실을 알려주고**, 그 다음 응시 계획을 입력할지 물어봄 — 즉 앱이 먼저 판단하고 먼저 말을 건 뒤에 정보를 요청하는 순서.
3. **TOPIK 페이지(트랙) 안에서는 그 외 추가 질문 없음** — 예외는 딱 둘: (a) 처음 가입할 때(=위 1번), (b) "자기소개"(프로필) 정보 자체가 바뀌었을 때(사용자가 직접 프로필을 수정한 경우).

## 구현 방향

### A. 공통 온보딩을 hub 레벨로 분리

- `state.profile`을 TOPIK I 앱 로컬 상태에서 **hub 공유 localStorage 키**(예: `jabi_profile`)로 이동 — Hangul/Basics/TOPIK II/TOPIK I 전부 같은 키를 읽고 씀.
- 공통 온보딩 화면(현재 1단계 "Basic info": 모국어·이전 학습기간·목표 학습량·일일 학습시간)만 남기고, **"Where you take TOPIK"/목표(2단계) 질문은 이 시퀀스에서 제거**.
- 트리거 지점: 각 트랙(Hangul/Basics/TOPIK I/TOPIK II)의 진입 스크립트 최상단에서 공통으로 `jabi_profile.onboardingDone` 체크 → 없으면 공통 온보딩(모달 또는 별도 화면)부터 보여준 뒤 원래 진입하려던 트랙으로 이어짐. 구현 방식(공용 JS 모듈로 뺄지, 각 트랙에 얇은 체크 코드만 심을지)은 Cursor 판단 — 기존 `hub/app/js/app.js`의 온보딩 UI(4단계 중 1단계 마크업)를 재사용.
- **모드(Catch/Mercy/Guide)·파트너(자모) 선택**은 TOPIK 전용 개념이므로 공통 온보딩에서 분리해 **TOPIK I/TOPIK II 트랙에 처음 진입할 때만** 별도로 물어보는 것으로 유지(이건 범용 정보가 아니라 TOPIK 학습 방식 설정이라 TOPIK 트랙 진입 시점이 자연스러움 — Paul 답변에서 "TOPIK 페이지 안에서 처음 가입할 때 예외"에 해당한다고 해석).

### B. TOPIK 응시 계획 — "내 페이지"에서 진도 기반 컨텍스트 노출

- 기존 `estimateReadiness()`(`app.js:1142`, [`ux-review-onboarding-flow-ko.md`](ux-review-onboarding-flow-ko.md) §1 참고 — 이미 존재하는 함수, 최소 시도 횟수 게이트 관련 개선 필요성도 그 문서에 별도 기록돼 있음)가 준비도를 계산하는 지점 재사용.
- **"내 페이지"(현재 TOPIK I "Me" 탭 `renderMe()`, `app.js` 내)**에서 준비도가 일정 임계치(기존 리뷰 문서 제안대로 "다회 시도 후"로 게이팅, 예: 3회 이상 연습 완료)를 넘으면: "실력이 TOPIK 응시를 고려할 수준이에요" 안내 + "응시 계획을 입력하시겠어요?" CTA 노출.
- 이 CTA를 눌렀을 때만 응시 예정 시기/지역 등을 물어보는 **작은 폼**(기존 온보딩 2단계 마크업 재사용 가능) — 강제 아님, 건너뛰기 가능.
- 이 정보가 이미 입력돼 있으면 다시 안 물어봄. 나중에 바꾸고 싶으면 "내 페이지"에서 직접 수정(아래 C 참고).

### C. "내 페이지"에 개별 항목 수정 가능한 설정 폼 추가

- 지금 "Redo onboarding"(전체 재실행) 버튼만 있는 것을, **개별 필드 수정 폼**으로 교체 또는 병행 — 모국어/학습량/시간 등을 각각 따로 고칠 수 있게.
- 이 폼에서 실제로 값이 바뀌면 그게 "자기소개에서 상태가 바뀐" 경우(Paul 답변의 예외 b) — 바뀐 항목에 따라 관련 트랙에 필요하면 재확인(예: 모국어를 바꾸면 UI 언어 관련 재확인 정도, TOPIK 응시 질문을 다시 강제로 띄우는 건 아님).
- 이 설정 화면이 Hangul/Basics/TOPIK II에서도 접근 가능해야 함(Paul 답변 취지) — MVP로는 각 트랙 상단 nav에 "내 정보" 링크를 추가해 TOPIK I의 Me 탭(=학습자 페이지)으로 연결하는 것으로 충분(완전히 새 페이지를 4개 트랙에 각각 만들 필요 없음, 기존 Me 탭을 hub 공용 학습자 페이지로 격상).

## 하지 않는 것 (스코프 아웃)

- 완전히 새로운 "학습자 페이지"를 처음부터 만드는 것 — 기존 TOPIK I "Me" 탭을 hub 공용 페이지로 승격시키는 방향으로 최소화.
- `estimateReadiness()`의 최소 시도 횟수 게이트 자체 수정 — 이건 [`ux-review-onboarding-flow-ko.md`](ux-review-onboarding-flow-ko.md) §1에 이미 별도로 기록된 이슈, 이번 스펙과 별개로 처리해도 됨(단, 같은 화면을 건드리므로 Cursor가 한 번에 처리해도 자연스러움).
- TOPIK II의 자체 파트너/모드 선택 여부 — 지금 파트너·모드 선택이 TOPIK I 전용인지 TOPIK II도 공유하는지 코드 확인 필요, Cursor 구현 시 실제 데이터 흐름 보고 판단.

## 회귀·검증 체크리스트

1. localStorage 완전 초기화 후 **Hangul을 먼저 열면 공통 온보딩(모국어 등)이 뜨는지** — 지금은 안 뜸(버그), 이게 핵심 확인 포인트.
2. 공통 온보딩에 "Where you take TOPIK"류 질문이 더 이상 없는지.
3. TOPIK I/II에 처음 진입할 때만 모드·파트너 선택이 뜨는지(공통 온보딩과 분리됐는지).
4. 연습을 여러 번 완료한 뒤 "내 페이지"에 TOPIK 응시 계획 CTA가 뜨는지, 건너뛰기 가능한지.
5. 이미 응시 계획을 입력한 사용자에게 다시 안 뜨는지.
6. "내 정보" 개별 필드 수정 폼이 실제로 값을 바꾸고 저장하는지.
